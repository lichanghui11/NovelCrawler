# 数据结构设计笔记

## 1. 核心决策：如何存储小说正文？

在爬取小说内容时，我们选择了使用 **字符串数组 (List of Strings)** 来存储每一章的段落，而不是将其拼接成一个巨大的字符串。

### 方案对比

| 方案 | 结构示例 | 优点 | 缺点 |
| :--- | :--- | :--- | :--- |
| **纯字符串** | `"第一段\n\n第二段..."` | 存储简单，看起来像普通文本文件。 | 后续处理困难（如转 EPUB），难以区分段落边界，需要处理复杂的换行符。 |
| **数组 (Lines)** | `["第一段", "第二段"]` | **结构清晰**，天然分段，易于模板渲染。 | JSON 文件体积微增（多了引号和逗号）。 |

### 为什么选择数组？
1.  **转换便利性**：在生成 EPUB 或 HTML 时，可以直接遍历数组，将每行包裹在 `<p>` 标签中，无需手动 split 字符串。
2.  **样式控制**：CSS 的首行缩进（`text-indent`）是针对 `<p>` 标签的，数组结构能确保每个自然段都是独立的 `<p>`。

## 2. 内容纯净度：纯文本 vs HTML 标签

**结论**：数组中只存储 **纯文本**，不包含 `<p>` 等 HTML 标签。

### 原因
遵循 **“内容与表现分离”** 的原则：
*   **数据层 (JSON)**：只负责存储“是什么”（小说文字）。
*   **表现层 (EPUB/Web)**：负责决定“长什么样”（加 `<p>`，加粗，字体）。

这样做的好处是，如果未来需要做数据分析（如词频统计）或转换为 Markdown，不需要先清洗掉 HTML 标签。

## 3. 最终 JSON 结构示例

```json
{
  "index": 1,
  "title": "第一章 景翰七年",
  "url": "https://m.shuhaige.net/...",
  "lines": [
    "这里是第一段内容。",
    "这里是第二段内容。",
    "..."
  ]
}
```
